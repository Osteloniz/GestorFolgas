## Incidente de produção corrigido

### Sintomas

- `POST /api/auth/sign-in/email` respondia `500` na Vercel, embora a interface mostrasse a mensagem genérica de e-mail ou senha incorretos.
- O bootstrap administrativo apresentava ocasionalmente “dados não encontrados”/erro ao carregar.

### Causa

O merge que adicionou o plugin administrativo do Better Auth passou a consultar novas colunas, mas a migration `src/db/migrations/0002_opposite_marvel_boy.sql` ainda não havia sido aplicada no Neon. Faltavam:

- `user.role`;
- `user.banned`;
- `user.ban_reason`;
- `user.ban_expires`;
- `session.impersonated_by`.

### Correção e validação

- A migration `0002_opposite_marvel_boy.sql` foi aplicada em 25/08/2026 ao banco configurado para produção.
- O registro da migration passou a existir na tabela de controle do Drizzle.
- Foi confirmado que o administrador ativo possui `role = admin` e vínculo válido com a conta de autenticação.
- Um login propositalmente inválido passou a responder `401 INVALID_EMAIL_OR_PASSWORD`, em vez de `500`.
- O bootstrap sem sessão passou a responder `401 Não autorizado`, comportamento esperado.
- Nenhuma migration adicional está pendente em razão desse incidente.

Não executar migrations em produção novamente sem conferir o ambiente e obter autorização explícita. Em uma instalação correta das dependências, o comando versionado é:

```bash
npm run db:migrate
```

## Regra aprovada para administradores

- O sistema pode manter vários administradores ativos simultaneamente.
- Cadastrar um novo administrador não desativa os existentes.
- Desativação é opcional e deve ocorrer somente quando for necessário revogar um acesso.
- Continua proibido desativar a própria conta.
- Continua proibido desativar o último administrador ativo.
- Todos os administradores precisam de senha e MFA TOTP para acessar o painel.

### Criar outro administrador sem e-mail transacional

O Resend não é necessário para criar administradores. O fluxo usa Better Auth e PostgreSQL:

1. Um administrador autenticado acessa **Configurações → Segurança → Novo administrador**.
2. Informa nome, e-mail e uma senha temporária forte.
3. Compartilha a senha temporária por um canal seguro e separado.
4. A nova pessoa entra em `/login`, troca a senha e configura um aplicativo TOTP, como Microsoft Authenticator ou Google Authenticator.
5. A pessoa salva os recovery codes e conclui o acesso.

O sistema não envia convite ou senha por e-mail. Não registrar ou compartilhar senha temporária, segredo TOTP, recovery codes ou token de sessão em logs, commits ou documentação.

## E-mail transacional e domínio

### Estado atual

- O código permanece integrado ao Resend.
- O Resend ainda não está configurado para produção porque o domínio/remetente ainda será definido.
- A ausência do Resend não afeta login, sessão, MFA ou criação de administradores.
- Ela afeta somente a confirmação por e-mail após uma escolha pública de folgas.
- Uma falha de envio é registrada como `FAILED` e não desfaz a escolha persistida.
- Nenhuma troca para Brevo foi implementada.

### Decisão em aberto

Foi avaliado o Brevo, que oferece plano gratuito com limite diário e pode validar um remetente individual. Ele não elimina, porém, as limitações de reputação e autenticação de domínio quando o remetente é um endereço gratuito.

A preferência atual é manter o Resend e usar um domínio autenticado, porque a integração já existe e isso reduz mudanças no sistema.

Antes de comprar um domínio, confirmar o endereço corporativo:

- se termina em `@outlook.com`, `@hotmail.com` ou `@live.com`, a organização não controla o DNS desse domínio; será necessário adquirir um domínio próprio para autenticação adequada no Resend;
- se a conta é Microsoft 365 com endereço como `usuario@empresa.com.br`, o domínio pode já pertencer à organização; nesse caso, não é necessário comprar outro, apenas obter acesso ao DNS.

Configuração sugerida quando houver domínio:

```text
From: Gestão de Folgas <notificacoes@mail.seudominio.com.br>
Reply-To: conta-corporativa@dominio-da-empresa.com.br
```

Usar um subdomínio de envio, como `mail.seudominio.com.br`, permite configurar SPF/DKIM do Resend sem alterar o MX usado pelo Microsoft 365 para recebimento.

Variáveis necessárias na Vercel, sem registrar seus valores:

```text
RESEND_API_KEY
EMAIL_FROM
```

As demais variáveis obrigatórias continuam documentadas em `.env.example`.

## Desenvolvimento em Windows e Linux

Compatibilidade entre Windows e Linux é requisito obrigatório.

- Não compartilhar nem copiar `node_modules` entre sistemas operacionais.
- Preferir um clone separado no filesystem nativo de cada sistema.
- Em cada novo clone/máquina, executar `npm ci` no próprio sistema.
- Não reutilizar binários nativos instalados no Windows dentro do Linux/WSL, ou vice-versa.
- Não usar comandos exclusivos de Bash ou PowerShell em scripts do `package.json` quando houver alternativa em Node.js.
- Nunca versionar `node_modules`, `.next`, `.env.local`, `.secrets` ou artefatos locais.
- A `.gitattributes` presente na branch `fix/ajuste_front` deve ser preservada no merge para normalizar finais de linha.

O problema observado nesta sessão ocorreu porque `node_modules` havia sido instalado no Windows e reutilizado no Linux:

- os atalhos em `node_modules/.bin` estavam sem permissão de execução;
- o `esbuild` instalado era o binário de Windows;
- o Vitest não encontrou o pacote nativo Linux do Rollup.

Isso era um problema da instalação local, não do código publicado. Para a alteração de administradores, `lint`, `typecheck` e `build` passaram. O teste de domínio equivalente também passou diretamente pelo Node; o Vitest ficou bloqueado apenas pela instalação cruzada de dependências. Em um clone Linux limpo, executar novamente:

```bash
npm run lint
npm run typecheck
npm test
npm run build
```
